# 共通投稿の設計と導入手順

食べログの口コミと手入力を、アプリ内では共通の `Post` として扱う。`kind` は内容の種類、`source` は取得元を表す。X・Zennなどの追加取得は行わない。

## 投稿モデル

| source | kind | 作成方法 |
| --- | --- | --- |
| tabelog | review | 既存の食べログ取り込み |
| manual | review / note / article | EmDash管理画面の「手入力投稿」 |

共通項目は `id`・`kind`・`source`・`title`・`body`・`date`・`externalId`・`sourceUrl`。公開Postにはアプリの `likeCount` も付ける。口コミだけが店舗名・店舗URL・評価を持つ。手入力の `externalId`・`sourceUrl` は `null` とし、入力欄も設けない。

- **review**：店舗名・訪問年月・0〜5の評価が公開に必要。店舗URLは任意。
- **note**：本文だけで書き始められる。タイトルは任意。
- **article**：公開にはタイトルと本文が必要。本文は今回プレーンテキストとし、改行を保持する。

手入力の投稿日時は作成時に初期設定し、管理画面で変更できる。未完成の下書きは保存できるが、公開と予約公開には種類別の検証を行う。食べログは既存の取得検証を継続する。

食べログのPost IDは従来の口コミID、手入力のPost IDは `manual-{CMSのコンテンツID}`。表示用スラッグの変更でも手入力のPost IDを変えず、食べログIDと区別する。改訂IDは投稿IDには使わない。

## 保存先と既存データ

既存の `reviews` コレクションを食べログ用として維持し、アプリ内で書いた投稿用に `entries` を追加する。公開APIでそれぞれをPostへ変換してまとめる。画面とカードはCMSの保存先を知らない。

| 役割 | 名前 |
| --- | --- |
| 共通モデル・API・一覧 | `Post`・`/api/posts`・`/posts` |
| アプリ内で書いた記録の保存先 | `entries` |
| 食べログの保存アダプター | `TabelogReviewStore` |
| 食べログの既存CMS保存先 | `reviews`（物理名を維持） |

食べログの接続部分は `TabelogReviewStore` と明示する。既存DBの名前を変えるためだけの移行は行わない。

一つのコレクションへコピーする案は採用しない。EmDash 1.3.1のスキーマAPIは既存フィールドの `required` 変更を `FIELD_UPDATE_REQUIRES_MIGRATION` で拒否する。さらにコピーではコンテンツID・改訂履歴・公開中の版・編集中の版・予約・ゴミ箱の移行が必要になる。既存保存先を維持すれば、これらの内容と状態をそのまま保持できる。

食べログの保存アダプターは `Review → Post → 既存CMS項目` と変換する。`Review` は食べログ取得結果と旧APIの互換用として残し、共通画面のデータ型には使わない。

既存の取り込みは未登録分を下書き追加する。下書き・公開・ゴミ箱を含めて食べログIDを照合し、DBの一意制約で同時取り込みの重複も防ぐ。既存の本文・公開状態・改訂は更新しない。手入力投稿はこの照合対象に含めない。

## APIと画面

- `GET /api/posts`：両コレクションの公開版だけを全ページ取得し、`{ posts, lastUpdatedAt }` を返す。
- `lastUpdatedAt`：食べログの取得に成功した最終日時。手入力の更新日時とは分ける。
- `GET /api/reviews`：従来の食べログ専用形式を維持する。
- `/posts`：共通の投稿一覧。既存の `/reviews` も同じ一覧を表示し、口コミIDのアンカーを維持する。
- 種類で絞り込みでき、評価順は口コミに絞った場合だけ提供する。

年月しか存在しない訪問日は `date.precision=month` とし、架空の日を付けない。手入力のノート・記事は `datetime` として投稿日時を使う。CMSの公開日時や取得日時を内容の日付へ流用しない。同月では年月だけの口コミを日時付き投稿の後に置き、前後不明の順序を捏造しない。同順位はIDで固定する。

手入力は元サービスURLを持たないため、カードでも省略する。食べログのいいね数はCMSに保持し、カードには[アプリ内いいね](post-likes.md)を共通表示する。本文はReactのテキスト表示を使い、HTMLとして実行しない。

## 依存の受け渡し

DIライブラリは追加せず、既存のファクトリーと関数引数を使う。HonoはHTTP応答、CMSアダプターは取得とPostへの変換、食べログスクレイパーは外部取得を担当する。手入力を仮のスクレイパーへ通さず、CMSから直接保存する。

## 導入手順

新規サイトは更新済みseedから両コレクションを作成する。セットアップ済みサイトではseedの修正だけでは反映されないため、先に次の準備を行う。

1. 環境を確認してD1をバックアップし、現在の `/api/reviews` の内容と件数を保存する。開発と本番は分ける。
2. 対象CMSでスキーマ管理権限のあるAPIトークンを発行し、手元の環境変数 `EMDASH_API_TOKEN` に設定する。チャットやコマンドの引数へキーを貼らない。
3. **旧バージョンのアプリが動いている段階で** `node scripts/prepare-entries.mjs https://対象のオリジン` を実行する。
4. 手入力用 `entries` の項目が作成されたことと、従来の口コミAPIが変わっていないことを確認する。同じ準備処理は再実行でき、既存項目の型や制約が異なる場合は停止する。
5. 本リポジトリのリリース手順に従って新バージョンを公開する。スキーマ未準備を空一覧へ置き換える処理は入れない。
6. 管理画面の「手入力投稿」で3種類を作成し、下書き・公開・予約の検証、共通一覧への表示を確認する。既存口コミの内容・ID・公開状態・履歴・予約・ゴミ箱と旧リンクも確認する。
7. 食べログ取り込みを実行し、新規分の下書き追加と再実行時の重複防止を確認する。

準備スクリプトは `reviews` の項目・内容・履歴・状態と、食べログ取得日時を変更しない。CMS内部テーブルへ直接SQLで書き込まない。

## 復旧

アプリを従来のリリースへ戻す。従来版は `reviews` だけを参照するため、既存口コミはそのまま使える。追加した `entries` は削除せず残し、作成済みの手入力投稿と履歴を保持する。DB全体の復元は、アプリの切り戻しで解決しない場合に、バックアップ以降の投稿を別途保全してから行う。
