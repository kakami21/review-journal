# コードコメント記述ルール

## 基本方針

- コメントは日本語で、対象固有の情報が伝わるよう具体的に記述すること。
- コードを読めば分かる処理内容を、そのままコメントで言い換えないこと。
- コードだけでは分からない理由、制約、前提、注意事項を記述すること。
- `APIルートの定義`や`データを取得する`など、別の処理にもそのまま当てはまる抽象的なコメントを書かないこと。
- 関数、APIルート、主要な処理ブロックには、目的に加えて、重要な入力、分岐条件、結果、副作用のうち理解に必要な情報を記述すること。
- APIルートには、そのエンドポイント固有の役割、許可するHTTPメソッド、正常時または異常時の主要な結果を記述すること。
- 複数行が必要な場合は、JSDoc形式または連続した行コメントを使い、1行に情報を詰め込まないこと。
- コメントと実装が食い違わないよう、実装を変更した際は関連するコメントも更新すること。

## APIルートの例

次のような、処理を分類しただけのコメントは避けること。

```ts
// APIルートの定義
app.post("/api/generate", (c) => generateReview(c.req.raw, c.env));
```

ルート固有の役割と主要な結果が分かるように記述すること。

```ts
// 店舗情報と利用者の感想を受け取り、過去の口コミを参考にした下書きを生成する。
// 生成結果のHTTPレスポンス作成はgenerateReviewに委譲する。
app.post("/api/generate", (c) => generateReview(c.req.raw, c.env));

// 生成APIへのPOST以外のリクエストを拒否する。
// 呼び出し側が許可されたメソッドを判別できるよう、Allowヘッダーと405を返す。
app.all("/api/generate", (c) => {
  c.header("Allow", "POST");
  return c.json({ error: "POSTで送信してください。" }, 405);
});

// Workerと口コミ参照元の稼働状態を確認する。
// 正常時はステータスと、取得できた文体サンプルの件数を返す。
app.get("/api/health", async (c) => {
  const styleSamples = await getReviewSource(c.env).getStyleSamples();
  return c.json({ status: "ok", writingSamples: styleSamples.length });
});
```

## コメントタグ

必要に応じて、次のタグを使用すること。

- `TODO:` 今後行う作業
- `FIXME:` 修正が必要な既知の問題
- `NOTE:` 実装を理解または変更するうえで重要な補足
- `HACK:` やむを得ない暫定実装と、その実装が必要な理由

## 表記

- タグは大文字の英語で記述すること。
- タグの直後には半角のコロンと半角スペースを置くこと。
- タグに続く説明は日本語で記述し、文末に句点を付けること。
- `TODO:` と `FIXME:` を継続して管理する場合は、可能であれば課題番号を付けること。

```ts
// TODO(#123): OpenAPIの定義を追加する。
// FIXME: エラー内容が生成API専用になっているため修正する。
// NOTE: このルートは静的ファイル用ルートより先に定義する。
// HACK: ライブラリ側の問題が解消されるまで暫定的に回避する。
```
