# タグによる本番リリースの共通規則

各プロジェクトで次のリリース運用を共通で使用する。
対象のサービス・DB・URL・設定ファイル・検証コマンド・追跡Issueは、導入先のリリース手順で具体的に指定する。

## CIと本番公開

- 作業PRとmainへのpushでは、テストと必要なすべてのビルドを実行する。本番公開は行わない。
- mainへのマージを開発完了、`vMAJOR.MINOR.PATCH`タグの新規pushを本番公開の契機として分ける。
- 公開ワークフローはタグ形式・対象コミット・main履歴・本番接続先を検証し、テストとビルドが成功してから公開する。検証用の接続先へ誤って公開しない。
- タグ更新・削除・強制pushでは公開しない。公開済みタグは付け替えず、修正には新しいバージョンを使う。

## 初回設定

- 本番公開専用のAPIトークンを、必要な対象と権限に限定して作成する。個人の開発用認証をCIへ流用しない。
- GitHub Environmentの`production`へ公開用Secretsを登録する。秘密値はチャット・コード・CLI引数へ貼り付けない。
- `production`ではタグの`v*`だけを許可する。承認者は設定せず、タグ作成を公開操作として扱う。
- ホスティング側のmain連携など、別経路の自動公開を確認して停止する。公開経路はタグによるActionsに統一し、確認せずに初回タグをpushしない。
- 実行環境に必要なSecretsを登録し、公開時に不足を検出して拒否する。アプリ実行用の秘密値をCIビルドへ渡さない。
- Cloudflareでは公式の「Edit Cloudflare Workers」テンプレートを基に権限を限定し、Workerの必須シークレット宣言で不足を検出する。
- 設定の確認状況と初回の公開結果は導入先のIssueに記録する。ローカル認証の成功だけで、GitHub上の公開を確認済みとしない。

## タグと公開後の確認

- 書き込み権限を持つ担当者がmainのCI成功を確認し、main上のコミットへタグを付ける。
- MAJORは互換性のない変更、MINORは互換性のある機能追加、PATCHは互換性のある修正に使う。プレリリースやゼロ埋めは本番用には受け付けない。

```sh
git fetch origin
git log -1 origin/main
git tag -a v1.0.0 origin/main -m "Release v1.0.0"
git push origin refs/tags/v1.0.0
```

- タグを複数まとめてpushせず、前回のRelease完了を待つ。本番公開を同時実行しないconcurrencyグループを設定するが、待機順の保証には使わない。
- Actionsの成功とSummaryのタグ・コミット・公開バージョンを確認する。
- 公開後のヘルスチェックをワークフローで実行し、HTTP 200と正常状態を確認する。アプリの主要機能も確認し、ヘルスチェックだけでDBや主要機能の正常性を断定しない。
- Webアプリの公開HTMLに`<meta name="release-version" content="v1.0.0">`のように実際のタグ名を埋め込む。タグ以外のビルドは`unreleased`とする。
- 同じタグのワークフロー再実行は同じコミットの再公開になる。通信失敗時も公開済みの可能性を考慮し、Summary・ログ・配信先の公開履歴を調べて判断する。自動再試行・自動ロールバックは行わない。

## GitHub Releases

- 公開成功後、既存タグを選びGitHub Releaseを作成する。概要、含まれるPR、利用者への影響、必要な手動操作、Actions実行URL、公開バージョンを記載する。
- Releaseの公開自体はデプロイを起動しない。Actionsでタグを作る仕組みは設けず、担当者によるタグpushを起点にする。

```sh
gh release create v1.0.0 --verify-tag --title v1.0.0 --generate-notes
```

## DB変更

- アプリ公開とDB変更は同じ操作で巻き戻せないため、リリースワークフローでDBマイグレーションを自動実行しない。
- DB変更が必要な場合はレビューし、本番対象を確認して、必要なバックアップと互換性のあるスキーマ変更を先に行う。
- 必要なマイグレーションの適用・照合が完了するまでタグをpushしない。必要なビューやテーブルと主要機能も確認する。
- D1の場合は、導入先に記載した本番DB名と設定を明示して`wrangler d1 migrations list`、`wrangler d1 export`、`wrangler d1 migrations apply`を使用する。

## 失敗時の復旧

- 公開前の検証失敗では本番を更新しない。原因を修正してmainへ取り込み、新しいタグを作る。
- 公開後のヘルスチェック失敗では、公開済みの可能性があるためログのバージョンと配信先の公開履歴を確認する。
- コードを戻す場合は直前の正常な公開バージョンを明示し、手動でロールバックする。復旧後はヘルスチェックと主要機能を確認し、タグは付け替えない。
- Cloudflareでは`wrangler deployments list`で履歴を確認し、正常なWorkerバージョンIDと設定ファイルを明示して`wrangler rollback`を実行する。
- コードのロールバックではDBのデータやスキーマは戻らない。旧コードとの互換性と、バックアップからの復旧を別途判断する。

## 検証

- 導入先のテストと各ビルド、本番接続先の検証を実行する。未実施の確認や外部設定不足は明記する。
- タグ形式・main履歴・タグ先の変更、本番／検証接続先の判定を検証する。
- CIはローカルの秘密設定ファイルなしで実行できるようにし、公開時は実行環境のSecrets登録を検証する。
