# チケットの書き方

この文書では、GitHubのIssueやAzure DevOpsのユーザーストーリー（US）・タスクなどをまとめて「チケット」と呼ぶ。USとタスクには同じ書き方を適用する。登録・担当者・ラベル・親子関係・完了操作は、導入先の管理ツールとプロジェクトの規則に従う。

## 基本方針

- 読み手に合う身近な言葉と短い文で書く。専門用語が必要なら初出で意味を添える。
- 確認できた事実と推測を分け、未確認の原因を断定しない。
- 秘密情報・認証ヘッダー・顧客情報を含めない。
- 同じ目的の既存のチケットを確認してから新規作成する。
- 日本語で書く場合は[日本語の文章](japanese-writing.md)の規則も使う。

## タイトルと本文

タイトルは作業の目的が分かる具体的な言葉で短く書く。プロジェクトに命名規則があれば従う。

チケットには、必要な項目を次の順で書く。管理ツールの入力欄が異なる場合は、対応する欄へ振り分ける。

1. **背景・目的**：困っていることと改善したいことを、2文程度で書く。
2. **対応内容**：利用者から見て変わることを3〜5項目程度で書く。調査なら、明らかにすることを書く。少ない項目で伝わる場合は増やさない。
3. **完了条件**：何を確認できたら終わりか、チェックリストで書く。
4. **補足**：判断に必要な技術詳細、関連するチケット、優先度の理由などがある場合だけ書く。長い説明は別資料へリンクする。

不具合では、環境・再現手順・期待した結果・実際の結果・影響・回避手段を、分かっている範囲で補足する。

## 参考資料

- [英国教育省のプレーンランゲージの指針](https://design.education.gov.uk/content-design/plain-language)：読み手に合う身近な言葉と短い文で伝えるための指針。
- [Microsoft Learn — Azure Boardsの作業項目管理](https://learn.microsoft.com/en-us/azure/devops/boards/backlogs/manage-work-items?view=azure-devops)：作業内容、受け入れ条件、再現手順などを記録するための公式ガイド。

「背景・目的」「対応内容」「完了条件」「補足」の構成と項目数の目安は、管理ツールをまたいで使うための独自ルールとする。
