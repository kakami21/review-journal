# Design — 実装の方針

## Context

作る目的と対象は [提案](proposal.md)、守る動作は [仕様](specs/review-promotion/spec.md) に書いている。この文書では、その動作をどう作るかを説明する。

口コミを編集・公開する管理システムはEmDash。サイトの処理を実行するプログラムをWorkerと呼ぶ。Cloudflareの保存先は、データベースがD1、ログイン状態などがKV、写真などのファイルがR2。検証と本番では、それぞれ別のプログラムと保存先を使っている。

| いまの仕組み | 今回の作り方 |
| --- | --- |
| `review-import-plugin.ts` の `run` は、管理者が必要な権限（`plugins:manage`）を持っているか確認してからPOSTという方法で操作を受け付ける | 同じ追加機能の中に別の処理を作り、食べログから取り込む操作と分ける |
| `CmsReviewStore` は本番の口コミとゴミ箱を最後のページまで調べ、新規だけを追加する | 重複を防ぐ考え方は使うが、追加専用の処理へ更新機能を詰め込まない |
| `seed/seed.json` の `reviews` は下書き、編集履歴、公開予約を扱い、食べログの口コミ番号（`source_id`）の重複を禁止している | 公開中の内容と最新の編集内容を別々に確認する。同時に同じ口コミを作ろうとした場合は、管理システムの重複禁止の仕組みも使う |
| `content-save-policy-plugin.mjs` は取得元の3項目を書き換える保存を拒否する | 既存口コミを更新するときは、編集する7項目だけを渡す |
| 検証と本番は別のWorker・D1・KV・R2を持つ。今は環境を見分ける変数と、プログラム同士の接続設定がない | 検証か本番かを区別する設定と、本番から検証への読み取り専用の接続を追加する |
| `src/worker.ts` は通常のページ表示をAstroへ渡し、CMS保守Cronという定期処理も動かす | この動きは残し、別のプログラムから読める処理だけを追加する |
| `get-public-reviews.ts` は公開中の口コミ全件と、食べログから最後に収集できた日時を返す | 公開口コミを返す今の処理を転用せず、今回必要な項目だけを読み取る |

インストール済みのEmDash 1.3.1のコードと、プログラムで扱える項目や値の種類を決める型定義も確認した。`withEmDashRuntime` は通常のページ表示以外でもEmDashの処理を使えるようにする。`handleContentList` は一覧を返す。`handleContentGet` は未公開の編集があれば最新の内容を返し、公開中の内容は `liveData` として別に返す。`handleContentUpdate` は編集の版情報（`_rev`）で同時編集を確認し、変更分を下書きに保存できる。

これはローカルのコードを読んで確認した結果。Cloudflare上で、プログラム間通信と組み合わせて動くかは実装時に試す。

## Goals / Non-Goals

**Goals — この設計で実現すること:**

- 公開中の口コミを読む処理、違いを判定する処理、保存する処理、結果を記録する処理を分け、それぞれ試せるようにする。
- 画面から送られた口コミ番号だけで保存を決めず、比較時の記録と、保存直前に読み直した内容で判断する。
- 口コミの保存と結果の記録の間で失敗しても、保存できたか不明な口コミをむやみに保存し直さない。

**Non-Goals — この設計では行わないこと:**

- EmDash内部の保存先を直接書き換えたり、別の公開APIを作ったり、口コミ以外もまとめて同期する仕組みを作ったりしない。APIは、プログラムから操作・取得できる処理を指す。
- 食べログの収集成功日時、CMS保守Cron、今ある新規追加専用の処理に、この機能を組み込まない。

## Decisions

### 1. 本番のプログラムから、検証の公開口コミだけを読む

2つのプログラムをつなぐ設定をService Binding、接続先の決められた処理を呼び出す通信をRPCと呼ぶ。この接続で、読み取りだけを許可する。

`src/worker.ts` から `PreviewReviewReader` という読み取り処理を、名前を付けて外へ提供する。本番の設定だけに `PREVIEW_REVIEWS` というService Bindingを追加し、検証Workerのこの処理を接続先にする。検証か本番かは、プログラム側の `APP_ENV` で見分ける。読み取りRPCは `preview` でだけ動かし、管理画面からの反映は `production` でだけ動かす。画面から送られた値で接続先や環境を変えない。

| RPCで提供する操作 | 内容 |
| --- | --- |
| `listPublished({ cursor })` | 公開中の口コミを少しずつ読む。`cursor` は、次にどこから読むかを示す値 |
| `getPublished({ sourceIds })` | 保存直前に、選んだ食べログの口コミ番号の公開内容を読み直す |

対象の投稿の種類は `reviews` に固定する。返すのは取得元の3項目、編集する7項目、内容の一致を確認する値（ハッシュ）、公開中の版を見分ける情報だけ。ユーザー情報、ログイン状態、下書き、サイト設定は返さない。一度に読む件数と指定できる番号の数には、プログラム側で上限を設ける。既存のZodという入力確認用のライブラリで、送受信する内容の形式を確認する。

公開一覧は、EmDashを使う準備をする `withEmDashRuntime` の中で、`handleContentList("reviews", { status: "published", limit: 100, cursor, orderBy: "id", order: "asc" })` を使う。1回100件まで、投稿番号の昇順で読む。現在の一覧取得は、個別取得と違って下書きの内容へ置き換えない。

個別に読み直すときは `source_id` で一致する口コミをすべて探し、重複を調べ、公開中か確認する。下書きがある場合は、公開中の内容を表す `liveData` が得られたことを確認する。下書きがなければ公開中のデータを読む。公開中の内容だと確認できなければ失敗にする。表示を速くするために一時保存した内容や、画面編集中の取得結果は流用しない。

本番へ接続する前に、公開中の本文と未公開の編集本文を別にした試験用口コミで確認する。一覧・個別取得の両方が公開本文だけを返すこと、プログラムを組み立てた後もRPCとEmDashの準備処理が動くことを試す。

| 比較した案 | 判断 |
| --- | --- |
| 本番から検証のデータベースを直接読む | EmDash内部の構造への依存と、環境をまたぐ接続権限が増えるため採用しない |
| インターネット経由で公開しているAPI（HTTP API）を読む | 今のAPIは全件と収集日時を返すもので、必要な取得元情報や、少しずつ読むための形式も異なる |
| 接続先を固定した読み取りRPC | 読み取りに必要な操作だけを提供でき、元の仕様に沿うため採用する |

### 2. 内容の違いを判定する処理では、保存を行わない

`src/lib/cms/review-promotion-diff.ts` に比較処理を作る。検証で公開中の内容、本番の公開中・編集中の内容、ゴミ箱、識別名、前回の記録を渡す。識別名は、URLなどに使う名前（スラッグ）のこと。

EmDashから返る情報を比較用に取り出す処理は、別にする。比較処理そのものはデータベースやWorkerを呼ばず、渡された情報から結果を返す。

比較する項目は、`restaurant_name`（店舗名）、`restaurant_url`（店舗URL）、`title`（タイトル）、`body`（本文）、`review_month`（訪問年月）、`rating`（評価）、`like_count`（いいね数）の順に固定する。タイトルと本文は、省略と値なし（`null`）だけを同じ扱いにする。空文字、空白、改行、数値を勝手に変えない。決まったJSON形式に並べたデータから、SHA-256という方法で内容の一致を判定する値を作る。取得元URLなどが食い違っていないかは別に確認する。

判定する順番は次のとおり。

1. 入力不正、どちらかの環境での口コミ番号の重複、取得元URLの食い違い、識別名の重複、本番のゴミ箱・公開予約があれば要確認にする。
2. 本番に同じ口コミがなければ新規にする。ただし、対応が分からない場合を「ない」と扱わない。
3. 前回の記録や公開中の内容と比べて、本番に独自の編集や別の下書きがあれば要確認にする。前回この機能で作った下書きが未編集のままなら、更新してよい。
4. 比較する項目がすべて同じなら差分なしにする。前回の記録がない場合は、同じ口コミが1件ずつと確認でき、別の編集もなければ、次回の基準として記録できる。
5. 前回の記録があり、本番の最新の内容が前回のままで、検証だけが変わった場合は更新にする。
6. それ以外の、すでに本番にある口コミの違いは要確認にする。

前回の記録には、内容の一致を判定する値、本番の投稿番号、前回保存した編集の版情報を残す。本文以外の独自編集や、別の下書きも見落とさないよう、最新の `_rev`、公開中と下書きの版、公開予約の状態を確認する。前回の反映後に通常の公開操作をしただけなら、編集内容と口コミの対応が保たれていることを確認して続けられる。

検証の内容を常に優先すると、本番で編集した内容を失う。更新日時だけで対象を絞る方法も、取りこぼしを判定できないため使わない。最初の版では両環境をすべて読み、選んだ口コミだけ保存直前に読み直す。全件を読んでいる間にも変更は起こるので、一覧がすべて同じ瞬間の内容だとは扱わない。

### 3. 比較結果を記録してから、条件を確かめて保存する

管理画面からの処理は、既存の追加機能の中に作る。以下は新しく作る、操作を受け付けるURLで、まだ実装されていない。共通のURLは `/_emdash/api/plugins/review-import/` で、送信方法はすべてPOSTにする。

| 操作を受け付けるURL | 送る情報と、返す結果 |
| --- | --- |
| `promotion/compare` | 接続先を固定して両環境を比較する。比較番号、4分類の件数、口コミごとの違いと変更前後を返す |
| `promotion/prepare` | 比較番号、選んだ口コミ番号、画面側で作った操作番号を受け取り、その操作の対象を固定して登録する。この時点では口コミを保存しない |
| `promotion/apply` | 操作番号を受け取り、まだ処理していない口コミを少しずつ順番に移す。進み具合と口コミごとの結果を返す |
| `promotion/status` | 操作番号で記録済みの結果を読む。保存できたか不明な口コミの再確認も、同じ操作番号に結び付ける |

どの処理でも、EmDashのログイン、必要な権限（`plugins:manage`）、本人が意図しない送信を防ぐ確認（CSRF保護）、本番環境かの確認を使う。操作した人は、EmDashが確認したログイン情報から取得する。送信内容に書かれた人物の番号は使わない。画面から接続先を選べる項目も設けない。

比較時の記録には、検証の内容を判定する値と取得元情報、本番の投稿番号・`_rev`・公開中と下書きの版・公開状態、分類を保存する。本番に下書きの版があるのに最新内容と公開中の内容を読み分けられなければ、更新可能にしない。

`prepare` は、その比較記録にある新規・更新の口コミだけを受け付ける。選択した口コミ番号は順序などの表し方を揃え、操作ごとに固定する。同じ操作番号で古い比較や別の選択内容を使わない。

`apply` は、選んだ口コミの検証公開版と本番の内容を読み直す。内容、対応、状態が変わっていたら、理由を表示して今回は移さない。保存は `withEmDashRuntime` と、EmDashの通常の作成・更新処理を通す。

- 新規は `handleContentCreate` を使う。`status: "draft"` で下書きを指定し、識別名には食べログの口コミ番号を使う。取得元の3項目と編集7項目を渡す。
- 更新は `handleContentUpdate` を使う。本番の投稿番号、比較時から変わっていない `_rev`、編集7項目、ログインから確認した操作した人を渡す。`status`、`publishedAt`、投稿の所有者、取得元の3項目は渡さない。公開中の口コミを `status: "draft"` に変更して公開解除することもない。
- 保存時に別の編集とぶつかったことを示す `CONFLICT` が返ったら、上書きを繰り返さず、その口コミの反映をやめる。新規作成で重複を拒否された場合は、食べログからの取り込みとの同時作成も考え、ゴミ箱なども含めて調べ直し、差分なしまたは要確認にする。
- 保存成功後は、本番の投稿番号、`_rev`、下書きの版番号を読み、予定の内容と一致したことを記録してから次回の比較基準を進める。

ボタンを押せなくするだけでは別のタブからの送信を防げない。画面から送られた本文をそのまま保存せず、保存してよいかは処理する側で判断する。

### 4. 比較・前回の内容・操作結果を分けて記録する

`migrations/emdash/0003_review_promotion.sql` で、この機能専用の記録場所をD1に追加する。SQLはデータベースへの指示を書く言語。実装時には、ファイル番号がまだ使われていないことを確認する。

| 記録場所の名前 | 保存する情報と制限 |
| --- | --- |
| `app_review_promotion_comparisons` | 比較番号、操作した人、作成日時、比較が完了したか |
| `app_review_promotion_comparison_items` | 比較番号と口コミ番号、分類と理由、変更前後、検証の内容を判定する値、本番の投稿番号・編集の版・公開状態。比較ごとの行番号は重複させない |
| `app_review_promotion_baselines` | 口コミ番号ごとに、本番の投稿番号、前回の内容を判定する値、最後に確認した公開中と下書きの版番号、最後の操作番号 |
| `app_review_promotion_runs` | 重複しない操作番号、比較番号、操作した人、選んだ口コミの組合せを判定する値、作成・更新日時、状態、どの処理が実行中かを示す情報 |
| `app_review_promotion_items` | 操作番号と口コミ番号の組合せを重複させず、操作、移す予定の内容を判定する値、変更前の内容と版、変更後の番号と版、結果と理由を残す |
| `app_review_promotion_lock` | 番号を1に固定。本番で動いている操作番号と処理の情報を残す。前の状態と一致する場合だけ書き換える方法で、同時実行を防ぐ |

比較結果は、全件を読み終えてから利用可能にする。差分なしの口コミを次回の基準として記録する場合は、同じ口コミが1件ずつで安全だともう一度確認する。この記録のために口コミ本文は保存しない。同時に別の比較が動いても、すでに進んだ基準を古い内容へ戻さない。

操作の登録と対象口コミの登録、保存結果と比較基準の更新など、関連する記録はまとめて保存する。D1の条件付き更新と `batch()` を使い、ひとまとめの記録をすべて成功かすべて失敗にする（トランザクション）。EmDashへの口コミ保存まで同じ処理にまとめられるとは考えない。食べログの収集日時を残す `app_review_sync` は読み書きせず、EmDash内部の保存先へSQLも発行しない。

### 5. 保存済みの口コミは保存し直さず、不明な結果を調べる

口コミごとの状態は、未処理（`pending`）、保存中（`saving`）、作成済み・更新済み・見送り・失敗・要確認（`created / updated / skipped / failed / needs-review`）の順で管理する。EmDashへ保存を依頼する前に、保存中であること、予定内容、変更前の版を記録する。成功が記録できた口コミは保存し直さない。

`prepare` で操作番号を先に登録し、画面が番号を受け取ってから `apply` を呼ぶ。画面を読み込み直しても `status` で結果を確認できるよう、操作番号を画面のURLに残す。操作番号を知っているだけで操作できるようにはせず、ログインと権限確認も行う。

処理は数回のPOSTに分ける。送信ごとに、どの処理が担当するかをD1へ記録する。記録は前の状態と一致する場合だけ更新する。同じ操作の二重送信には進み具合だけを返し、別の操作には処理中と返す。操作全体の使用中の記録は最後の口コミまで残し、送信ごとの処理の担当記録だけを途中で解除する。通常は、処理終了時に必ず動かす `finally` で、自分が担当した記録だけを解除する。古い処理が新しい処理の記録を変えることを防ぐ。

中断が疑われても、時間がたっただけで保存中の口コミを未処理に戻さない。通常の通信断では、裏側の処理と終了時の後片付けが終わるのを待ってから、同じ操作番号で再開する。プログラムの強制終了やD1障害で記録が残った場合は、運用担当者が操作番号、送信ごとの番号（要求ID）、Workerの動作記録で、元の処理が終了したことを確認する。終了を確認できなければ新しい保存は始めず、結果確認だけを許可する。

終了を確認できたら、次の順で調べてから未処理分を再開する。

1. 本番の投稿番号、または食べログの口コミ番号で一致する1件をEmDashから読み直す。
2. 保存前の状態と予定内容に加えて、現在の公開中・下書きの版、編集履歴、操作した人を突き合わせる。
3. 同じ反映の保存だと確認できた場合だけ、結果の記録と次回の基準を補う。内容が同じというだけで、別の人の編集を今回の成功扱いにしない。
4. EmDashから明確な保存失敗が返った口コミは失敗として残す。成否不明、同時保存の衝突、判別不能の口コミは要確認にし、自動で保存し直さない。

失敗した口コミは、結果を確認してから改めて比較できる。まだ処理していない口コミは元の操作を続けられるが、その都度、比較後に変わっていないかを確認する。後から編集された口コミを、古い比較結果で上書きしない。

最初の版では、別の汎用的な処理管理の仕組みや、CloudflareのQueue・Durable Objectは追加しない。D1の記録だけで、停止した処理の特定と安全な再開ができることを、接続前に失敗を意図的に起こして試す。処理の終了が分からないのに、成功したことにはしない。

### 6. 今の管理画面に、比較・選択・結果確認を追加する

`review-import-page.tsx` に本番用の表示を追加する。いまの食べログ取り込みのボタンと結果表示は残す。比較中、口コミの選択、反映の確定、結果確認を分けて管理する。

最初は何も選ばず、新規・更新だけを選べるようにする。要確認には理由を表示する。本文の変更前後は文字として表示し、HTMLが含まれていてもプログラムとして動かさない。反映中は二重操作を抑え、通信が切れた場合は「結果を再確認」を使えるようにする。

完了時は、作成・更新・見送り・失敗の件数、要確認の理由、本番の口コミへのリンク、元へ戻すための情報を表示する。内部の `needs-review` は見送り件数に含め、理由で区別する。通常の画面には、権限名や編集の版番号、内容を判定するハッシュなど、実装上の情報を並べない。

### 7. 本番とは別の保存先で試してから公開する

通常の `npm run dev` は、検証サイトの実データへ接続する。本番と同じ役割のプログラムへ書き込む試験には使わない。専用の試験設定で、読む側と移す先のWorker、別々のD1、必要な管理システムの保存先を用意する。本番と同じ役割として動かす試験用プログラムにも、本番のD1・KV・R2は渡さない。

試験用データで、接続、公開中の内容だけの取得、複数ページ、下書きの作成・更新、別の編集が入った場合、ログインと権限、不正な送信の拒否、二重実行、保存直後の結果記録失敗、元へ戻す操作を確認する。既存の `tests/cms.integration.mjs` は参考にするが、本番や通常の検証データを変更する試験には使わない。

## Risks / Trade-offs

- 組み立て後のプログラムでRPCとEmDashの準備処理がつながらない可能性がある → 名前付き処理が残り、実際のEmDashから公開中の内容を読めることを最初に試す。成立しなければ本番へ接続せず設計を見直す。
- 全件を読んでいる間に口コミが変わる → 決まった順に、次の位置を示す値を使って読み進める。移す直前に選択分の内容と本番の版を確認する。全件が同じ瞬間の内容だとは扱わない。
- 口コミの保存と結果の記録を一度に確定できない → 保存前の記録と編集履歴を突き合わせる。確認できない口コミは要確認にする。
- 元の処理の終了を確認できず、再開を待つ場合がある → 進み具合と操作番号を残す。動いている処理や結果が不明な保存を繰り返さず、失敗を起こす試験で再確認と再開の手順を確認する。
- EmDashの履歴整理で、古い版が残り続けるとは限らない → 変更前の版番号と、変更前の内容・状態もこの機能の記録へ残す。履歴から戻せなければ、管理者が記録と現在の内容を比較して管理画面で編集し直す。
- 反映しただけでは公開されない → 結果から本番の口コミ一覧を開き、内容を確認して公開する。

## Migration Plan

1. 処理ごと・管理画面からの操作・環境設定のテスト、既存テスト、型チェック、検証と本番用プログラムの組み立てを通す。同時実行の制限と中断後の再開も、試験用の保存先で確かめて記録する。
2. 試験用D1へ記録場所の追加SQLを適用する。追加した記録が空でも、前回の記録がなく内容が違う既存口コミを要確認にすることを試す。
3. 本番データベースの対象、バックアップ、元へ戻す手順、現在のWorkerの版を確認し、本番にも追加SQLを適用する。既存の保存項目やデータは変えない。
4. 検証Workerへ読み取りRPCを先に公開する。その後で、本番へ環境の区別、接続設定、管理画面の機能を公開する。
5. 公開口コミの取得、管理画面、食べログ取り込みを確認して、両環境を比較する。口コミを移す操作は管理者が選んで行い、公開はさらに別の操作にする。
6. プログラムや設定を戻す場合は直前のWorkerの版へ戻す。この機能の記録場所と既存データは残す。誤作成の下書きはゴミ箱へ移し、誤更新は変更前と現在の版を比べて戻す。戻した口コミは再比較し、古い基準で再び上書きしない。
