# Tasks — 実装するときの作業一覧

チェックが付いていない項目は、まだ作業していないもの。この文書には、作るものと、その作業が終わったかを確かめる方法を書く。

以下のWorkerはサイトの処理を実行するプログラム、D1はデータベース、KVはログイン状態などの保存先、R2は写真などのファイル保存先を指す。管理システムは口コミを編集・公開するEmDashのこと。

## 1. 本番とは別の試験用サイトで、公開中の口コミだけを読めるようにする

- [ ] 1.1 口コミを読む側と移す先の、専用の試験設定・データを用意する。プログラムと保存先（D1・KV・R2）が本番・通常の検証サイトと別であることを、設定のテストで確認する。
- [ ] 1.2 管理システムから公開中の内容だけを取り出す処理を追加する。下書きだけの口コミ、公開予約、ゴミ箱を除くこと、未公開の編集を移さないこと、読めない内容を読めたことにしないことを、処理ごとのテストと実際のEmDashで確認する。
- [ ] 1.3 `src/worker.ts` に、別のプログラムから読み取りだけを依頼できる `PreviewReviewReader` を追加する。一覧と口コミ番号での読み直し、全ページの取得、不正な入力の拒否、重複の検出をテストする。Astroの通常のページ表示とCMS保守Cronの既存テストも通す。
- [ ] 1.4 両環境の設定に、検証か本番かを区別する情報を追加する。本番だけに、検証のプログラムへ接続する `PREVIEW_REVIEWS` を設定する。プログラム用の型定義と設定テストを更新し、試験用の2つのWorkerを組み立てた結果で、通信処理（RPC）が公開中の内容だけを返すことを確認する。
- [ ] 1.5 プログラム間で送受信する内容、環境の区別、試験用サイトの起動・データ投入・後片付けの方法を開発資料へ書く。その手順で接続の試験を再現できることを確認する。

## 2. 同じ口コミか、何が変わったかを判定する

- [ ] 2.1 `review-promotion-diff.ts` に、比較する7項目を決まった形に揃え、内容の一致を判定する値を作り、変更前後を取り出す処理を追加する。項目の省略と値なし（null）、空文字、改行、いいね数だけの変更、管理システムが付けた情報の除外をテストする。
- [ ] 2.2 本番の公開中の内容・最新の編集内容・ゴミ箱を取得する処理を追加する。後続のページもすべて読み、下書きを読み込めない場合に公開中の内容を最新の編集内容と思い込まないことをテストする。
- [ ] 2.3 新規・更新・要確認・差分なしを判定する。本番での独自編集、別の下書き、前回移したままの下書き、前回の記録がない既存口コミの違い、一度公開した後の再反映を、条件ごとのテストで確認する。
- [ ] 2.4 重複登録、取得元URLの食い違い、URLなどに使う識別名の重複、公開予約、ゴミ箱の確認を、本文の比較より先に行う。本文が一致しても反映を止めるテストを追加し、判定表を仕様書または開発資料へ書く。

## 3. 比べた内容と操作結果をデータベースに残す

- [ ] 3.1 追加設定のSQLファイルに使う番号が空いているか確認する。比較・比較した口コミ・前回の記録・反映操作・口コミごとの結果・二重実行を防ぐ記録の保存先を、試験用D1に追加する。番号の重複登録を拒否し、既存の保存先や収集成功日時を変えないことを確認する。
- [ ] 3.2 比較が終わったこと、安全に一致した内容を次回の基準にすること、操作番号の登録、選んだ口コミの固定を実装する。途中の読み込み失敗、同時比較による記録の巻き戻し、同じ操作番号での対象変更をテストする。
- [ ] 3.3 同時に動く反映操作を一つにし、送信ごとにどの処理が実行中かを記録する。同じ操作の二重送信、別操作の拒否、数回に分けて処理する間の別操作の禁止、古い処理による記録変更の拒否を、D1を使う処理のテストで確認する。
- [ ] 3.4 保存前の「保存中」（`saving`）、変更前の内容と編集の版、保存結果、次回の比較基準を記録する。関連する記録の保存が途中で失敗したら、半端な成功記録が残らないことをテストする。保存する項目と処理状態の変化を `DATABASE_DESIGN.md` に追記する。

## 4. 本番の編集を守りながら保存し、途中から再開できるようにする

- [ ] 4.1 比較したときの番号と選んだ口コミ番号で反映操作を準備し、保存直前にその口コミを読み直す。未選択や書き換えられた対象を拒否し、検証での内容変更・公開解除、本番の変更、口コミの対応変更があれば移すのをやめることをテストする。
- [ ] 4.2 新規の口コミを、食べログの口コミ番号と同じ識別名で下書きとして作る。取得元の3項目も残す。同じ口コミの登録を拒否された場合だけ本番を調べ直し、食べログからの取り込みと同時でも重複を作らず、内容が違うものを成功扱いにしないことをテストする。
- [ ] 4.3 既存口コミを更新するときは、本番の編集の版情報（`_rev`）と編集7項目だけを保存に使う。取得元情報・投稿の所有者・公開日時・公開状態を保つ。実際の試験用EmDashで、公開本文を保った下書き保存、保存直前の別編集の保護、取得元を変更できない確認処理を試す。
- [ ] 4.4 結果を記録した口コミは保存し直さず、まだ処理していない口コミから再開できるようにする。途中失敗、通信断、口コミの保存直後に結果の記録だけ失敗する場合を意図的に起こして確認する。保存できたか確かめられない口コミは要確認にし、再保存しない。
- [ ] 4.5 通常終了時に実行中の記録を解除し、異常終了で記録が残った場合の再確認手順を作る。まだ動いている処理や、時間がたっただけの処理を勝手にやり直さないことを試す。元の処理の終了を確認した後、同じ操作の未処理分から再開できることも確認する。
- [ ] 4.6 新規下書きのゴミ箱移動、変更前の版から戻す操作、古い編集履歴が消えていた場合に記録した変更前の内容と比べる方法を資料へ書く。試験用EmDashで、反映後に追加した編集を失わず、戻すかどうかを判断できることを確認する。

## 5. 管理者だけが操作できるようにする

- [ ] 5.1 `review-import-plugin.ts` に、比較・操作の準備・保存・結果確認の処理を `promotion/compare`・`prepare`・`apply`・`status` として追加する。送信方法はPOSTにする。EmDashのログイン、必要な権限（`plugins:manage`）、意図しない送信を防ぐ確認（CSRF保護）、処理する側での本番判定を使う。未ログイン、権限不足、不正な送信、検証環境で拒否されるテストを追加する。
- [ ] 5.2 操作した人はログイン情報から確認し、送信内容に書かれた人や接続先、投稿の種類をそのまま採用しないことをテストする。入力と返す結果の形式をZodで確認し、比較番号・操作番号の使い方と送受信する内容を資料へ書く。
- [ ] 5.3 既存の食べログ取り込み（`run`）と公開口コミを返す処理（API）を維持する。追加した処理が収集成功日時、手入力投稿、写真、画面部品、設定を変更しないことを、送信から結果が返るまでのテストで確認する。

## 6. 管理画面で違いを確認し、移す口コミを選べるようにする

- [ ] 6.1 本番の「口コミの取り込み」に比較する操作を追加し、4分類の件数、店舗名、タイトル、理由、変更前後を表示する。複数ページ、0件、取得失敗を画面のテストで確認する。
- [ ] 6.2 最初は何も選ばず、新規・更新の口コミだけを選択できるようにする。選んだ分だけの反映、要確認の口コミを選べないこと、二重操作の抑止、本文にHTMLがあってもプログラムとして実行しない表示を確認する。
- [ ] 6.3 操作番号を先に確定して画面のURLに残し、その後に保存を始める。通信断や画面の再読み込み後の「結果を再確認」と、未処理分からの再開を作る。件数、口コミごとの結果と理由、本番の口コミへのリンク、元へ戻すための情報を、画面と裏側の処理を通して確認する。
- [ ] 6.4 既存の食べログ取り込み表示を維持し、比較から本番での公開までの利用手順をREADMEまたは管理画面の資料へ書く。その順序で、試験用サイトの口コミを一部選んで反映できることを確認する。

## 7. 全体の動作と、公開・元に戻す手順を確認する

- [ ] 7.1 試験用の2つのWorkerと実際のEmDashを使い、通常の反映、公開中の内容の保護、同時編集、権限、二重実行、一部失敗、保存できたか分からない場合、再開、元へ戻す操作を試して記録する。通常の検証サイトと本番のデータが変わっていないことも確認する。
- [ ] 7.2 `npm test`、`npm run check`、`npm run build:preview`、`npm run build:production`、`npx openspec validate promote-preview-reviews --strict` を実行する。今まで動いていた機能を壊していないこと、組み立て後のWorkerに読み取り通信処理が残っていること、本番だけに接続設定があることを確認する。
- [ ] 7.3 `docs/deploy-production.md` に、データベースへの追加設定、検証側の通信処理から先に公開する順番、公開した版の記録、公開後の主要機能の確認、プログラムを戻しても操作履歴を残す方法を書く。試験用サイトで同じ順序を再現し、本番へ公開できる状態にする。
